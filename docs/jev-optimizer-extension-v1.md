# PipiUI Jev 优化扩展规格 v1

- 状态：已按批准计划实现检索首版；workspace 功能验证已通过。真实仓库的 Jev 评分与完整 Agent 提速仍未证明，不能将功能完成写成性能目标达成。
- 日期：2026-09-20。
- 扩展身份：`jev-optimizer`，显示名「Jev 优化」。
- 决策来源：用户要求用 `to-spec` 综合既有讨论，并明确要求独立可选扩展，避免没有 TypeSafe key 的用户承担依赖。
- 交付范围：源码、可复现评测入口与结果报告；没有打包或重启 PipiUI。用户随后提供 key 并要求对比，真实 API 仅使用生成的合成代码，没有上传工作区源码。

## 后续优化：显式有界深搜

`code_search` 新增可选 `deep: true`，仅用于开放式 auto/semantic 查询；省略或 false 保持首版行为，exact/symbol 路由明确拒绝 deep。它不是新 Agent，也不替换 `grep`、`read`、`code_nav` 或 Pi runtime。

- 在同一次调用内复用本地召回，沿 Tree-sitter 解析的相对导入、简单 Markdown 相对链接和现有名称型调用关系补充证据。callee 调用点先解析为定义，不能把调用点冒充实现。相对 `.js` 导入允许对应 `.ts`/`.tsx` 源文件；不实现包别名、完整模块解析器或类型系统。
- 确定性路径优先：强精确锚点或至多三个起始候选文件时不请求 Jev；起始候选文件超过三个且扩展可用时，最多调用一次现有重排来选起点。后续逐步读取不发云请求；不新增 Choice 协议或第二个索引。普通模式原有的可选重排不受影响。
- 已发现的实现、入口及关系按组排列，不以相关性分数阈值删除。最终只分配一轮 R#、写一份工具结果；内部读取不记作主模型已读，只有实际展示的预览进入 seen ledger。关系在正文以 R# 展示，完整关系保存在 `details.deep` 及结果 JSONL 头部。
- 有界探索：最多三个起点、六个展开步骤、两层关系、十二次符号查询；深搜自身最多读取十份文件、单文件 256 KiB、累计 512 KiB。导入列表、目标定义、图返回、候选及最终 topK 都有上限；截断必须标记 `incomplete` 和预算原因，不把尚未检查的候选称为无关。
- 初始范围校验和本地展开各有 1500ms 等待预算，可选重排沿用自己的 1500ms 总预算；这些不包括原始检索/索引准备。慢异步文件等待会停止等待，既有符号图缓存会定期让出调度，但同步文件系统/解析无法被 JS 强行中断，故不承诺整个工具的硬实时上界。取消后不再启动后续深搜操作；已有符号图任务仍受其旧接口“不支持内部取消”的限制。文件计数/字节预算指深搜显式读取，不包括符号图自身的索引维护。
- 所有新增候选仍校验项目范围、path/glob/exclude 与真实路径；Jev 仍只接收受限、过滤后的起始片段。无 key、服务故障或关闭扩展时，确定性深搜可独立工作。

这是有限证据定位，不保证找全，也不根据一次未命中宣布实现不存在；主模型仍须核对原文。此前合成实验只支持机制可行性，不能据此宣称普遍提速或更低费用。

## 问题陈述

代码定位经常退化为「主 LLM 猜一个词 → 检索 → 阅读 → 换词再搜」。单次本地检索通常不是主要成本，重复的模型轮次、大量不相关结果和过早读取完整文件才是需要验证的优化对象。

用户希望一次提交更多检索角度、在允许的项目范围内扩大本地召回，再让 Jev 快速缩小候选范围，最后由主 LLM 阅读必要源码并完成理解。

同时，TypeSafe Jev 是需要独立凭据的云端评价服务，不是所有 PipiUI 用户都拥有 key。不能把其安装、账号、网络或费用变成基础检索的前置条件；不能以优化名义改变 `grep` 的精确匹配或 `read` 的原文读取语义。

## 解决方案

增加独立、可选的 **Jev 优化扩展**，首版为现有代码检索提供可选的相关性重排序服务。

职责严格分开：

| 所属部分 | 负责 | 不负责 |
| --- | --- | --- |
| 现有 Code Retrieval 扩展 | 本地查询、索引与 fallback、多查询合并、候选和片段准备、范围限制、最终 R# 与结果格式 | TypeSafe 凭据、云 HTTP、Jev 模型契约 |
| Jev 优化扩展 | 设置页 key、云端评价、调用预算、响应校验、可选服务的注册和撤销 | 扫描磁盘、创建第二套索引、读取任意路径、注册替代检索工具 |
| 现有 `read` / `read_spans` | 按用户或模型选择读取原文 | 自动上传整份文件、被 Jev 摘要替代 |
| 主 LLM | 理解目标，必要时一次给出查询变体，阅读结果并推理 | 每个候选都单独发起一次 Jev 工具调用 |

用户安装并启用 `jev-optimizer`、填写 key 后，适用的 `code_search` 自动使用它，不必更换主模型或每次显式调用新工具。没有扩展、没有 key、扩展关闭或服务失败时，基础检索仍能完成。

首版不扩展到 browser、AX、computer use、主模型路由或记忆。它们可以在未来复用 Jev 的服务实现，但不是本规格的交付条件。

## 用户故事

1. 作为没有 TypeSafe key 的用户，我希望继续使用现有检索和阅读工具，以便不为可选优化注册额外服务。
2. 作为有 key 的用户，我希望安装一个独立扩展即可启用优化，以便不改变 Pi runtime 或主模型设置。
3. 作为用户，我希望设置页明确说明查询和源码片段会发送给 TypeSafe，以便理解启用后的数据流和费用来源。
4. 作为用户，我希望 key 使用现有 secret 设置保存，以便不把凭据写入项目配置、日志或 Git。
5. 作为用户，我希望按项目选择是否启用该扩展，以便敏感项目仍可保持纯本地检索。
6. 作为提出代码问题的用户，我希望一次检索可覆盖多个有差异的查询角度，以便减少主模型反复猜词。
7. 作为指定范围的用户，我希望任何查询变体都遵守相同的 path、glob 和排除规则，以便扩大召回不会越过已指定边界。
8. 作为使用精确字符串或符号查询的用户，我希望该查询仍由确定性机制处理，以便不被模型判断静默过滤。
9. 作为阅读结果的主模型，我希望获得少量相关代码引用和有用片段，以便先判断阅读价值再展开函数体。
10. 作为排查跨模块问题的用户，我希望保留多个相关候选，以便不会因只押中一个文件而漏掉调用方、依赖或测试。
11. 作为用户，我希望重复命中的相同代码范围被合并，以便同一函数不会因为多组查询占满结果。
12. 作为用户，我希望 Jev 故障时仍得到本地检索结果，以便云端优化不成为新的故障点。
13. 作为取消任务的用户，我希望取消同时传递给局部查询和 Jev 请求，以便停止后不再继续后台计费或返回迟到结果。
14. 作为用户，我希望能区分「本地索引降级」和「Jev 未应用」，以便理解结果而不误以为检索完全不可用。
15. 作为用户，我希望关闭扩展后停止新的 Jev 调用，以便撤销云端优化不会要求杀掉 PipiUI 宿主。
16. 作为使用 Worker 的用户，我希望已获授权且挂载扩展的 Worker 复用同一检索路径，以便不需要专门的 Jev 子代理。
17. 作为使用 `read_spans` 的主模型，我希望 R# 仍引用真实代码范围，以便重排不会制造、改写或串用引用。
18. 作为产品维护者，我希望有默认关闭、故障回退和云载荷的自动契约测试，以便以后更新不破坏无 key 用户的体验。
19. 作为评测者，我希望分开比较多查询召回和 Jev 重排，以便不会把本地检索改进误算成 Jev 的收益。
20. 作为用户，我希望性能结论同时报告召回质量、整体耗时、模型轮次和费用，以便不被单次 API 的速度宣传误导。

## 实现决策

### D1. 独立可选扩展，不是基础包依赖

- `jev-optimizer` 使用现有扩展发现、设置、启停与分发机制。不得加入基础必需扩展集合，不得因安装 Code Retrieval 自动启用它。
- 不把 TypeSafe key 或 Jev 网络代码放进 Code Retrieval 的设置和实现；Code Retrieval 不静态导入 Jev 的包。
- Jev 扩展不注册新的模型可见搜索／阅读工具，不覆盖现有四个检索工具，也不注册冒充通用聊天模型的 provider。
- 双方通过一个版本化的、同 Pi 进程内的可选重排契约协作。没有提供者时立即走本地路径，不等待网络或超时。
- 该契约只服务本次检索重排，不建设通用插件服务市场或第二套调度系统。

### D2. 基础调用兼容与宽召回入口

- 保留 `code_search` 的必填 `query` 以及现有 `mode/path/glob/topK`。
- 新增可选 `queryVariants`：最多三个非空短字符串，表示同一问题的额外检索表达；加上主 query 最多四组。trim 后按稳定顺序去重。
- `query` 始终是排序所针对的原始问题。变体只帮助本地召回，不能替换原始意图，也不能携带另一套 scope。
- 不在检索内部新增一次 LLM 调用来生成变体。主模型可在已有工具调用中提供；没提供时仍能使用单 query 重排。
- 新变体参数只用于开放式查询。显式 `exact/symbol`，以及主 query 的 `auto` 路由落到 exact/symbol 时，若带变体则返回清楚的参数错误；不能静默丢弃变体或改成语义查询。
- 单 query 的 exact/symbol 路径不请求 Jev。精确 `grep`、原文 `read`、关系查询 `code_nav` 和 `repo_map` 完全不变。
- 没有可用 Jev 服务且未提供变体的原调用，必须保留今天的候选、顺序、输出预算与 fallback 语义；不偷偷扩大扫描。
- 用户显式提供变体时，纯本地模式也能合并这些查询。它不要求 key，也不因缺少 key 报错。

### D3. 宽召回复用现有检索，不假定已有全策略并行

当前实现优先使用本地语义检索；没有命中才进入 lexical/symbol/exact fallback。它不是每次同时跑完所有后端再合并。

新路径按以下规则执行：

1. 仅在显式提供变体，或本次可用 Jev 服务接受该开放式查询时进入宽召回。
2. 每组查询复用既有路由和 fallback；不为「更宽」另外起一套索引、embedding 服务或目录爬虫。
3. 查询组并发上限为二；每组内部保持现有后端契约，并传递同一取消信号。
4. 候选目标是最终 `topK` 的三倍，最多 100 个；最终结果仍遵循既有 `topK`（当前默认 20）。这些是首版预算，不是速度结论。
5. 相同项目相对路径、起止行范围视为同一候选；保留所有命中来源，避免重复占位。
6. 多查询用稳定的 reciprocal-rank fusion 合并，常数为 60；不直接比较不同查询／后端的原始分数。并列时以主查询名次、相对路径、行号确定顺序。
7. 一组查询失败不能丢掉其他组已有结果。所有组无结果时才报告实际无命中；所有组失败时保留原有错误恢复路径。
8. 范围扩大仅发生在当前项目及用户允许的 path/glob 内。不得删除显式范围、越过 symlink containment，或扫描其他项目、全局 Pi 家。

### D4. Jev 只处理已准备好的候选

- 重排位置在本地候选集合形成之后、分配最终 R# 和生成 inline previews 之前。
- Code Retrieval 准备带相对路径、行范围、可用符号名、命中依据和少量上下文的候选。Jev 不获得文件系统读取接口。
- 请求内候选使用明确、局部的标签，例如 `candidate-1`。这不是最终 R#，不得持久化为新引用，也不得接受服务端新造的路径或标签。
- 优先复用已有 snippet；补取邻近源码仍由本地候选准备完成，遵守排除规则和读取预算。网络等待前的预读不得标记为「主 LLM 已读」。
- 最多评价本地排序前 64 个候选；请求完整序列化后的 UTF-8 字节数最多 64 KiB，单候选源码片段最多 768 字节。先按完整行截短片段，再减少候选，不截断 JSON 或静默截掉原始问题。连原始问题和最小候选也放不下时，跳过 Jev 并说明预算原因。
- 超出评价窗口的候选留在本地尾部，不伪称已被 Jev 判断为不相关。
- 不把整个文件、整个仓库、原始 `read` 返回值或完整主会话历史发给 Jev。即便扩大本地扫描，也不等于扩大云端上传。

### D5. 评价与排序契约

- 使用 TypeSafe 的 System One 评价接口，不使用 chat-completions，也不引入一整套 Vercel AI SDK 作为必要依赖。
- 一次请求共享原始问题和候选状态，针对每个候选提出 Score 问题：0=无关，1=只有提及，2=理解问题所需的关联代码／调用／测试，3=直接承载目标行为或实现。评分准则包含原始问题，不让候选源码充当指令。
- 首版使用一个请求完成评价，不逐候选串行请求、不反复 tournament、不做自动云端重试。
- 校验回答类型、完整候选集合、有限数值及范围。未知标签、缺失回答、重复回答、NaN 或不合约响应使整次重排回退，不拼接半份可靠性未知的排序。
- 保持若干候选而非只选一个文件；按有效评价分降序，分数相同时保留本地名次。全部评价无区分度时保持本地排序。
- 不把服务返回的 confidence 直接当作正确率保证；首版不设置未经校准的「0.8 就安全」门槛。
- 对主查询中显式完整路径、完整符号或带引号的精确文本所形成的确定性强命中，保留在前部，Jev 只能重排其他候选。强命中识别不得退化为「任意词出现就保护」。强命中超过结果预算时，维持可解释的本地次序并报告截断，不能让 Jev 任意丢弃。
- 最终才分配会话内 R#。既有 ref 的含义不被覆盖；Jev 回答不能直接进入 `read_spans` 的路径解析。

### D6. 服务发现、生命周期与取消

- 提供者身份固定为 `jev-optimizer`，契约版本为 1。调用输入包含候选快照、原始问题、scope 身份、预算和取消信号，输出仅为评价或跳过／失败结果。
- 复用 Pi 已有的进程内 `pi.events` 作为协作传输；新增的是双方约定，不假定目前已有 reranker 服务注册中心。不得把 `emit` 的返回值当作同步 RPC 答案。
- 约定 `pipiui.retrieval-reranker.discover.v1`、`pipiui.retrieval-reranker.provide.v1`、`pipiui.retrieval-reranker.withdraw.v1` 三个 channel。Code Retrieval 先订阅 provide/withdraw，再发 discover；Jev 先订阅 discover，再主动发 provide，收到 discover 时也发 provide。这样任一方后加载均可完成握手；不依赖扩展 factory 顺序。
- provide 携带协议版本、提供者身份、当前实例代际及进程内可调用的 availability/rerank 函数，不携带 key。Code Retrieval 保存合法服务引用，在工具执行时调用；若握手尚未完成则本次立即走本地，不为发现等待超时。不是把函数序列化进 RPC、会话记录或 tool result。
- 重复的同实例 offer 幂等；withdraw 只撤销匹配实例，旧回调不能覆盖新实例。availability 以当前有效启用态和凭据就绪态回答，不靠旧 env 的存在推断仍获授权。未安装、未挂载、未启用或无 key 时不得发远程请求。
- 订阅必须有 disposer；会话结束清除服务引用与监听。每个 Worker 使用自己的 Pi 进程、event bus 与已授权扩展集合；Jev 包须通过既有 registered-extension remount 路径挂载，不能假定主会话注册会跨进程生效，不新增 Worker 工具或扩大授权。
- 用户禁用扩展后不得再发新的 Jev 请求；已发出的请求应尽力取消，迟到回答不得改变返回结果。不能依赖杀死或重启 PipiUI 宿主来停止云端调用。
- 当前扩展挂载与 secret env 是会话启动时的快照，不能虚构成完整热卸载。第一条切片须为 Jev availability 复用或补齐由宿主有效扩展状态驱动的撤销检查；关停时撤销服务并阻止新上传，不建设通用热加载系统。key 被清除／替换时，旧凭据实例同样失效；新 key 依现有新会话／Pi 子进程重载规则生效，设置页如需新会话必须明示，不要求重启 PipiUI 宿主。
- 一次 Jev 评价的总等待预算为 1500 ms（包含请求阶段），无自动重试。超时只放弃本次优化；用户取消则结束整次搜索，不转入无视取消的 fallback 扫描。
- 首版不做跨调用或跨项目的云评分缓存，不新增常驻网络 sidecar。

### D7. 凭据与最小设置体验

- Jev 扩展提供一个项目范围的 secret 设置 `ext.jev-optimizer.apiKey`，复用现有 schema `format:secret` 和宿主扩展 secret vault 通道。
- 此设置不是 session `secret_vault_mount` 的别名。设置页填 key 后必须通过已有扩展密钥注入路径抵达主会话与获准 Worker；不能只保存字段却没有消费者。
- 运行时从宿主投送的 `EXT_JEV_OPTIMIZER_APIKEY` 读取并作为显式 API key 交给薄适配器。key 不写入项目设置 JSON，不加入模型目录，不进查询、候选、结果卡或日志。
- 扩展启用本身就是优化开关，不再增加一个默认关闭、容易漏开的第二开关。启用且配置有效 key 后，适用查询自动使用优化。
- 无 key 时设置页给出可关闭的说明「未配置 TypeSafe key，基础检索仍可使用」，不阻塞 Composer，不强制跳转注册，不重复弹出授权仪式。
- 凭据复用当前宿主的 project-scope 扩展 secret namespace：项目之间隔离，当前为内存保管、宿主退出后清空；不新建持久化存储或把项目 key 特判成跨项目共享。项目启用态、检索数据和结果仍按项目隔离，不写全局 `~/.pi`。
- 不新增可任意重定向携带凭据请求的 endpoint 设置。首版使用官方 API，记录实际返回模型身份用于评测；主模型不变。

### D8. 数据边界

- 启用说明明确：原始查询、相对路径／符号和受限源码片段会发送给 TypeSafe；该扩展是额外云接收方。
- 不因为 SDK 开源而宣称模型离线或数据不出机。官方本地权重、直连 API 的完整保留条款尚未核实；不得把 Gateway 的宣传自动套给直连 API。
- 现有检索排除规则继续有效；额外云载荷不得包含项目外内容、`.git`／`.pi` 内部数据、凭据文件或私钥文件。敏感候选可以保留在本地结果中，不必为上传而删除本地命中。
- API key 只出现在鉴权头；错误输出采用稳定短错误码，不原样转储请求、响应 body 或 headers。
- 已知敏感字段应脱敏，但不能把模式匹配宣传为「保证源码没有秘密」。用户可通过不启用扩展或排除路径保持这些内容本地。
- 不上传本地索引、不新建云端代码索引、不存储原始云请求快照。

### D9. 降级与可观察性

| 条件 | 行为 |
| --- | --- |
| 无 Jev 扩展／未挂载／未启用 | 立即本地检索；不等待、无网络、无虚假的故障提示 |
| 已启用但无 key | 本地检索；状态说明 key 缺失，不让普通工具失败 |
| exact/symbol、零候选、候选无需筛选或预算不足 | 跳过 Jev；保留相应本地结果 |
| 超时、鉴权错误、限流、网络错误、服务错误、非法回答 | 返回云调用前已保存的完整本地排序；不额外重搜一遍，不丢候选 |
| 一个查询变体失败 | 保留其余查询结果并报告局部 fallback |
| 用户取消／提供者撤销 | 取消远端；用户取消不继续运行新扫描；迟到结果丢弃 |

- 本地 `details.provider` 仍按既有规则说明真正提供候选的索引／rg 路线，不得改成 `jev` 来假装 Jev 是索引。多查询混合来源用新增的可选 sources 元数据保留每组实际来源，不能把其中一个 provider 宣称为全部结果的来源。
- 保留现有本地 `details.degraded` 语义，Jev 状态以可选 `details.reranker` 独立记录：provider、applied/skipped/fallback、稳定 reason、候选数、实际评价数、耗时，以及 API 返回时可得的输入 usage。
- 无扩展的老调用不强行添加 Jev 噪声字段。应用或失败时给一条简短路由说明；不把普通排名说明写成索引故障。
- 不覆盖既有本地 score 的含义；若暴露 Jev 分数，使用独立可选字段并说明其量纲。
- 默认日志只存状态、数量、时长与 usage，不存 query、源码、key 或响应全文。既有 results JSONL／R#／inline 数量和 tokenBudget 契约不变。
- 主模型收到的 inline 源码 preview 继续遵守每段至多 6 行、所有片段合计至多 1000 token 的现有硬上限；不能因为默认 tokenBudget 为 4000 就放宽它。Jev 请求预算与主模型输出／`read_spans` 预算分开，不借优化增加主模型阅读量。

### D10. 非目标和设计取舍

选择单个可选重排序接缝，而不是：

- 给每次 `grep/read` 加一次网络调用：会改变精确工具语义，也可能只增加延迟。
- 把 Jev 注册成通用主模型：其输出契约不支持开放式代码／文本生成。
- 另起 Jev 搜索工具／云索引：会产生平行检索路径和第二套引用体系。
- 把 SDK、key 和设置直接塞入 Code Retrieval：违背用户要求的独立可选扩展边界。
- 为首版建设通用优化代理或自动任务规划器：超出已讨论范围。

## 测试决策

### T1. 主测试接缝

以现有 `executeCodeSearch` 的可观察输出为主接缝，注入本地检索与可选评价服务，断言返回引用、排序、降级信息、上传调用次数和取消行为。优先扩展已有工具级测试，不依赖真实 Jev 或大模型才能跑 CI。

适配器保留小型 HTTP 契约测试；扩展设置／挂载测试复用现有 host 测试。这两类只验证工具接缝无法看见的鉴权投送和线协议，不另建平行测试框架。

### T2. 必须覆盖的功能契约

1. 无优化扩展、扩展关闭、缺 key 三种状态：网络调用数均为零；老参数调用与基线结果兼容。
2. key 经扩展 secret 设置进入 vault，项目配置／结果／错误日志不含明文；主会话与获准 Worker 均能消费，未挂载扩展的 Worker 不获得服务。
3. Code Retrieval 单独安装可用；Jev 单独安装不产生残缺搜索工具；两者加载顺序互换行为相同。
4. 多查询去重、并发上限、范围继承、候选池上限、稳定合并顺序；一组失败保留其他结果。
5. explicit exact/symbol 不请求云；强精确命中不被错误低分淘汰；跨文件答案不被强制压成单个文件。
6. 上传仅含候选摘要，符合总预算；内部预读不污染 SeenRangeLedger；云排除候选仍可出现在本地输出。
7. 合法评分改变名次但不制造／改变路径和范围；R# 分配与随后 `read_spans` 的原文、预算及去重一致。
8. 未知／缺失／重复标签、类型错误、非有限数值、超时、401、429、5xx、断网均返回保存的本地排序，且不自动重试。
9. 用户取消、禁用扩展、session shutdown、旧请求迟到均不能触发新请求或污染新结果。
10. 本地索引降级与 Jev fallback 独立可见；Jev 未调用不能报告 applied；费用未返回时不能填造一个估算实价。
11. `grep/read/code_nav/repo_map` 的工具归属、schema 和现有回归保持不变；不新增第二个检索工具名。

### T3. 评测设计

复用当前检索 eval 的 fixture 与工具行为检查，新增一组固定代码定位任务。任务至少覆盖：自然语言描述、中英文表达、标识符／路径／报错精确查询、词汇不一致、跨文件行为、明确范围、大量重复命中、无结果、索引降级。

每个案例记录人工确认的目标文件／符号及必要关联范围，而不是把另一个 LLM 的排序当作唯一真值。

比较三组，使用相同仓库快照、排除规则、最终 topK 与输出预算：

- A：现有单 query 本地检索。
- B：新增多查询宽召回、只使用本地融合排序。
- C：与 B 完全相同的候选集合，再应用 Jev。

另单列单 query + Jev，区分变体收益和评分收益。实际 agent 实验固定主模型与任务预算，不临时给某一组更好的提示或更多工具机会。

记录：目标文件／符号 Recall@K、首个正确结果名次、必要关联代码覆盖、输出 token 估计、端到端定位成功率、主 LLM 搜索／阅读轮次、检索及完整任务 p50/p95、每个成功任务的总费用、Jev fallback 比例。冷／热索引分别记录；token 估计与 API 实际 usage 分栏。

### T4. 验收与发布措辞

- 功能验收先满足 T2；没有真实 key 也必须能完整验证无 key 路径和模拟云端路径。
- 固定金标集上，强精确命中不得新增漏检；C 相对 B 的目标 Recall@K 不得下降。失败案例必须列出，不用平均分掩盖。
- 是否「加速」以真实端到端数据判断，而不是 API 单次延迟。作为首轮实验目标，完整定位任务的中位耗时或主 LLM 输入 token 至少改善 20%，且定位成功率不下降；这是设计目标，不是已经取得的结果。
- 成本可能上升，必须报告总费用。只有总费用也下降才能声称「更省钱」；没有足够样本时只能报告探索性结果。
- 准备不少于 30 个定位案例，计时比较至少重复三次；输出样本数与原始结果，不声称由此证明所有仓库均更快。
- 真正带 key、发送源码的实验只使用明确允许外发的测试仓库／夹具，属于后续实施验收，不在本次文档任务中执行。
- 未取得真实 API／端到端证据时，可以交付「可选扩展接线和契约测试通过」，不能交付「PipiUI 已提速」。默认不把它变成所有用户的必选路径。

## 范围之外

- 替换 Pi runtime、CUA Driver、主 LLM、embedding 模型或现有本地索引。
- Browser／AX／computer use 优化、工具／模型／子代理自动路由、记忆筛选。
- Jev 本地权重部署、训练／微调、云端仓库索引、任意服务端 endpoint、多供应商优化平台。
- 自动生成大量查询的第二次 LLM 规划调用、递归搜索代理、无上限自动扩范围。
- 改写 `grep/read` 原文语义、绕开项目／扩展授权、增加 Worker 桌面能力。
- 修改锁定基础提示词；必要指导仅放工具自身描述或本扩展的能力提示层。
- 自动购买额度、注册账号、读取或上传真实用户敏感项目来凑 benchmark。
- 在本轮修复历史文档状态、清理无关工作区、打包或重启宿主。
