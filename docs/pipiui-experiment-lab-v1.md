# PipiUI 原型实验规格 v1 — 主聊天驱动修订

- 日期：2026-09-21。
- 状态：后续已按用户“分票然后实现”的授权完成核心源码与集成验证；实际范围、失败检查及未验证项见末尾验收记录。文档本身不构成新的执行授权。
- 交付范围：实验扩展、原型 Skill、可选结果查看与相关 runtime 接缝；本轮不运行付费模型实验、不提交、不打包或重启 App。
- 发布位置：本地规格及 `.scratch/prototype-experiments/issues/` 九票；执行计划为 `prototype-experiments`，不创建外部 issue／PR。
- 替代关系：本修订取代同路径旧版的“先建设 OS 沙盒／面板操作，再逐票接入实验”前提。旧执行计划 `pipiui-experiment-lab-v1` 已取消，不再是实施依据；历史代码与证据保留，不据此自动删除或重做。
- 能力身份：沿用可选扩展 `experiment-lab`。用户主要感知的是 Boss 的原型实验能力，而非必须操作的独立工作台。

## 问题陈述

用户与 Boss 讨论代码设计、优化或替代方案时，希望先验证再投入正式实现。例如，用 Jev 替代当前某项功能是否有收益，不能只靠模型推理或一次演示判断。

用户需要 Boss 自己完成最小原型、真实测试和公平对比，尤其包括大量真实 Pi 会话及多进程并发测试。长测试期间，用户应能继续聊天，随时问进度、查看某个 Pi 或停止测试，而不必管理终端窗口、编写调度脚本或填写实验表单。

原型可能失败或被放弃，因此不能污染正式工作区；测试通过也不应自动合并原型。报告必须把实际结果、失败、成本和未证明事项说清，最终是否正式采用仍由用户决定。

实施前已有基线记录、命令运行、Worker、worktree、终端和观察能力，但尚未组成这条主聊天驱动的流程。实施前接缝核对与本次实际验收在补充说明中分开列出，不能把工具存在或源码通过当成已安装 App 验收完成。

## 解决方案

交付“实验扩展 + 原型实验 Skill”，把实验作为 Boss 的按需工作方式。用户在主界面直接说：

> 我想用 Jev 替代当前这部分功能。做个原型，用 4 个 Pi 并发测试，原实现和候选各跑 10 轮，比较正确性、耗时和 token 消耗。

以上数字是用户输入示例，不是固定默认值。目标、轮次和并发数可以由用户指定，也可以由 Boss 根据任务给出并声明有界的执行设置。

核心体验：

1. Boss 理解替代目标、现有实现、候选假设及不能退步的要求；能从上下文确定的事情不再询问。
2. 保存当前代码和配置基线，确定共同测例、初始状态、验证方法及预算。
3. 在受管理的实验 worktree 中制作足以验证假设的最小原型，不提前做完整产品集成。
4. 自动调度真实 Pi 单次运行及必要的命令／浏览器测试，支持多个 Pi 进程并发。
5. 持续记录状态、工具活动、增量日志和结果；Boss 可主动查询，重要变化可触发提醒。
6. 在主聊天中给出有证据的对比、失败案例、收益、代价和未验证内容；需要时可打开原型或终端。
7. 用户选择保留现状、继续试验、放弃，或要求按选中方案正式实现。

这里的“沙盒”是 **worktree 承载的实验工作区**，用于分开原型、运行数据与正式开发；不承诺操作系统级文件、网络或恶意代码隔离，不引入 Docker 前提。

| 组成 | 用户价值与责任 |
| --- | --- |
| 实验扩展 | 提供实际工具、运行登记、worktree 用途约束、结果记录、状态／日志查询、取消和比较能力 |
| 原型实验 Skill | 指导 Boss 何时进入实验、怎样调用工具、组织原型和测试、判断证据及交回采用决定 |
| 现有 Worker 与测试设施 | 执行原型修改、真实 Pi 任务、命令和必要的浏览器验证，尽量复用现有机制 |
| 运行承载 | 运行真实 Pi；按需使用 RPC、PTY／终端，tmux 是可选承载方式，不是必装依赖 |
| 可选实验面板 | 查看进度、差异、结果和历史；不开面板也能完成核心流程 |

命令测试、Pi 行为测试和界面原型验证按实验目标组合，不要求每个实验都同时使用三者。大量真实 Pi 测试和多进程并发属于核心范围，不以仅有脚本 benchmark 或多个终端窗口替代。

## 用户故事

1. 作为开发者，我希望只在需要验证设计假设时使用实验，以便普通修复不增加前置流程。
2. 作为用户，我希望在主聊天用自然语言发起原型测试，以便不用先进入独立工作台。
3. 作为用户，我希望不用填写实验 ID、JSON、命令和逐轮调度表，以便把精力放在目标和结论上。
4. 作为用户，我希望 Boss 只询问无法从上下文确定的关键问题，以便实验不会变成长时间访谈。
5. 作为开发者，我希望 Boss 明确当前实现和替代假设，以便原型验证的是我真正关心的问题。
6. 作为用户，我希望当前未提交修改被保留且明确是否进入基线，以便实验对应正在讨论的代码。
7. 作为开发者，我希望基线、输入和验证规则在对比前确定，以便不能事后挑选有利条件。
8. 作为用户，我希望仅制作必要的候选，以便不会为无意义的变体消耗时间和模型费用。
9. 作为开发者，我希望原型在独立 worktree 中实现，以便不会改乱正式工作区。
10. 作为用户，我希望原型成功和测试通过都不会自动合并，以便仍由我决定正式实现方向。
11. 作为开发者，我希望已有基线和历史结果能够继续读取，以便产品形态调整不丢失证据。
12. 作为评测者，我希望运行的是真实目标 Pi，而不是模拟器或 PATH 中碰巧存在的另一个 Pi，以便结果对应实际运行时。
13. 作为评测者，我希望看到实际生效的模型、thinking、工具、Skill、扩展和提示配置，以便知道比较改变了什么。
14. 作为用户，我希望一次发起多测例、多方案、多轮 Pi 测试，以便减少重复操作并观察波动。
15. 作为用户，我希望多个真实 Pi 进程能够同时测试，以便大量实验不必全部串行等待。
16. 作为用户，我希望能指定并发数，并看到排队和实际并发情况，以便控制资源占用。
17. 作为开发者，我希望并发 Pi 的可写工作区、会话和临时状态相互独立，以便结果不被串写污染。
18. 作为用户，我希望测试有轮数、时间和资源预算，以便不会失控运行或无限重试。
19. 作为用户，我希望长测试不因 Boss 一次回复结束而停止，以便可以继续处理其他对话内容。
20. 作为用户，我希望随时问“跑到哪了”，以便获得当前方案、测例、轮次和阶段，而不是模型猜测。
21. 作为 Boss，我希望按游标读取新增日志，以便无需反复读取全部输出或截取所有终端整屏内容。
22. 作为用户，我希望阶段结束、失败、需要输入及整批结束时收到适当提醒，以便不必持续盯着终端。
23. 作为用户，我希望 Boss 忙时也不丢失最终状态，以便通知未及时展示不影响后续查询和汇总。
24. 作为用户，我希望必要时能打开某个测试的真实终端查看或接管，以便检查复杂 Pi 交互问题。
25. 作为用户，我希望没有安装 tmux 也能使用核心实验流程，以便不为开始测试先搭建基础设施。
26. 作为用户，我希望停止某一轮或整批实验，以便保留已取得的结果并避免继续调度不需要的工作。
27. 作为用户，我希望一轮失败不会默认拖垮其他独立测试，以便仍能取得完整的比较信息。
28. 作为用户，我希望重开会话后能查看已有记录，且不会自动重跑收费任务，以便恢复操作不造成重复消耗。
29. 作为评测者，我希望区分加速完成的并发测试与专门的并发压力测试，以便指标口径符合测试目的。
30. 作为评测者，我希望报告说明并发、缓存、顺序和限流条件，以便不把环境差异误判为方案优劣。
31. 作为用户，我希望成功、失败、超时、取消、无效及未启动项都可见，以便报告不筛掉不利结果。
32. 作为用户，我希望看到原始样本和重复运行的波动，以便不凭一次好运决定方案。
33. 作为用户，我希望数值标明来源、单位及缺失状态，以便 AI 解释不能冒充实测数据。
34. 作为用户，我希望 token、估算费用和实际账单不被混淆，以便正确理解实验成本。
35. 作为用户，我希望界面原型能被实际打开和交互验证，以便截图或主观描述不能代替真实操作。
36. 作为用户，我希望在主聊天看到结论、失败案例和证据引用，以便不用进入面板才能理解结果。
37. 作为用户，我希望候选更差或证据不足时 Boss 直接说明，以便不会被预设的赢家误导。
38. 作为用户，我希望能选择继续试验、保留现状或正式采用，以便实验自动化不替代产品决策。
39. 作为开发者，我希望正式采用时获得版本、差异、验证结果和待去除试验代码的交接，以便原型不会被直接当作生产实现。
40. 作为用户，我希望关闭扩展后普通开发不受影响、实验错误可关闭、清理不误删唯一原型，以便这项能力始终可选且可控。

## 实现决策

### D1. 能力所有权与最小范围

- 沿用可选实验扩展，拥有实验领域状态和操作；不把实验加入基础必需能力，不强制每个开发请求走原型流程。
- 首版优先走通“主聊天发起、worktree 原型、真实 Pi 并发、可观察运行、对比回主聊天”的纵向路径。命令和浏览器是按需使用的验证方式，不先建设一个与用户流程分离的平台。
- 尽量复用 Worker、worktree 管理、Pi 运行与观察机制；仅补实验用途、trial 归属和必要适配，不另建常驻通用 Job 服务、调度平台或适配器市场。
- Git 项目为首版工作区来源；非 Git 项目明确说明当前能力边界，不擅自初始化仓库。
- 不预设候选数量或赢家。通常从现状与一个有区别的候选开始，更多候选来自用户要求或明确的验证需要。

### D2. 扩展与 Skill 的分工

- 扩展提供自解释的工具名称、描述、参数和结果。基本操作不应完全依赖 Skill 才能正确调用。
- 实验 Skill 属于实验扩展，使用已有的按启用状态发现 Skill 资源机制；按需加载流程，不把完整方法常驻所有会话。
- Skill 负责识别明确的实验请求、选择测例和指标、组织最小原型、调用现有执行与观察工具、解释证据及等待用户采用。运行登记、并发上限、状态、取消和合并约束由代码负责，不仅写成提示词。
- 复用已有 prototype 的逻辑／UI 探索方法，但不把一次性原型的轻量习惯理解为可以省略对比测试。
- 单工具说明放在工具指导中，只有启用该能力才适用的指导归扩展。不得修改锁定的基础系统提示词。
- 扩展关闭或所需工具未挂载时，Skill 不得虚构能力；说明缺失项。不得因为实验能力关闭而改变普通开发行为。

### D3. 主聊天、请求与授权

- 明确请求“做个原型测试对比”后，Boss 在已有授权和已声明预算内自动完成流程；不要求用户再输入内部动作词、批准每个 trial 或打开面板。
- 用户只是问“这个方案怎么样”时，先回答或建议实验，不自动启动付费测试。目标有实质性歧义时只问必要问题。
- 预算未指定时，Boss 根据任务给出并声明有界设置后执行，不要求填写配置表。具体数值不是本规格预先固定的产品常量；扩展必须拒绝无界或非法设置。
- 新的源码接收方、未授权凭据使用、对外发布或突破已声明预算，仍需相应授权；已经授权的模型使用不再逐轮重复确认。
- 主聊天能完成发起、查询、查看失败、停止、再试和表达采用决定。面板只读同一权威状态，不能成为执行开关或第二份业务状态。

### D4. 实验对象、身份与记录

| 对象 | 必要内容 |
| --- | --- |
| 实验 Experiment | 项目、语义身份、问题、修订、基线、方案、测例、指标、预算和比较目的 |
| 方案 Variant | 假设、代码版本或 Pi profile、有效配置、候选差异与冻结指纹；包含现状基线 |
| 测例 Case | 任务输入、初始状态、执行步骤、固定验证规则及相关资源需求 |
| 测试批次 Test Batch | 某修订下方案 × 测例 × 重复轮次的执行集合、顺序、并发策略和预算 |
| 单次运行 Trial | 所属批次／方案／测例／轮次、真实运行身份、工作区、Pi 会话、承载方式、阶段和结果 |
| 报告 Report | 完整执行集合、比较口径、指标与差值、失败和缺失项、结论边界及证据索引 |
| 采纳 Adoption | 明确用户来源、所选修订／方案指纹及正式实现交接，不是合并命令 |

- 模型操作的实验、方案、测例、批次和 trial 使用可读语义标识；由 Boss 自动命名，不要求用户填写。caller-chosen 与运行时分配的身份保持区分，既有 opaque runId 只承担机器完整性校验。
- 每个 trial 关联精确运行实例；事件需携带归属和序号，旧运行不能覆盖重试后的新状态。
- 状态、原始日志、指标和证据持久化且可重建。主聊天摘要、面板、通知及 AI 解释均不是第二个结果权威。
- schema 显式演进并保留旧记录。历史命令／srt 结果仍按当时的承载与限制显示，不改写成新的 worktree／Pi 并发结果。

### D5. Worktree 实验区与原型生命周期

- 实验沙盒采用受管理的 worktree／独立工作目录；目标是分开原型、单次运行状态和正式开发，不是执行不可信恶意代码的安全边界。
- 默认基线对应当前讨论的工作内容，包括声明范围内的已跟踪修改和明确相关的未跟踪源码。记录纳入、排除及版本信息，不提交、stash、重置或覆盖用户主树与 index。
- 基线、候选与共同验证输入形成可追溯的冻结版本。冻结期间出现并发改动时不能发布混合版本；后续修改进入新修订。
- 工作树由现有管理器创建和登记，不手工接管其他 Worker 的工作树。原型 Worker 只修改分配的实验区及方案范围。
- 增加明确的实验用途／不会自动合并的生命周期策略。原型成功、verify 通过、接受结果、恢复收尾和会话合并均不能将实验改动自动带回正式树。
- 不冒用 secretary 等角色、不故意制造失败或 dirty 来阻止合并。普通开发 Worker 的默认行为保持不变。
- 候选冻结后再测量；每个并发 Pi 使用独立可写工作区、会话和临时状态，不共享可变 worktree。共享只读输入或缓存须声明，不能污染对比条件。
- 清理只处理已登记且允许清理的本实验资源；默认保留报告和唯一原型。放弃原型与删除唯一修改需要明确用户意图。

### D6. 真实 Pi 运行与承载

- Pi 行为实验必须启动真实 Pi 进程／会话，不由模型角色扮演或普通脚本替代。命令类 benchmark 可以非 LLM 执行，不额外启动 Pi 来包装每个命令。
- 显式绑定目标 Pi runtime，记录实际可执行程序身份和版本，不依赖全局 PATH 上碰巧找到的同名 Pi。
- 记录真实生效的任务、模型、thinking、工具、Skill、扩展、提示与依赖配置。比较只改变声明的变量；不支持的配置明确报告，不能静默换成另一个 agent 完成任务。
- 每轮会话与可变资源归属当前项目和本次运行；凭据按现有授权引用，不复制其他项目状态、全局 trust 或完整宿主环境，不向日志倾倒密钥。
- 复用现有 Pi 进程与 Worker 生命周期，在其外提供薄的实验适配。可使用真实 Pi RPC 或已有 PTY 评测路径；不为了统一传输方式重写整套评测框架。
- 终端是可查看、必要时可接管的执行现场，不是唯一结果来源。打开终端指向已登记的同一运行，不重新启动第二个 Pi；人工输入应留痕，可能影响可比性的运行单列。
- tmux 不作为首版必装依赖。若接入可选 tmux 承载，需探测可用性、绑定自己的 session／pane，并经过同一状态和结果合同；缺失时不得显示虚假的 attach／保活能力。
- 本规格要求测试跨 Boss 的模型回合持续运行，不要求跨应用退出持续运行。后者只能由经验证的承载模式明确承诺，不能仅因使用终端或 tmux 字样就视为具备。
- 从 Electron 启动 Node 必须遵守既有 Node 模式及防递归断路器。实验不得自动启动、替换、退出或重启 Canonical App。

### D7. 多进程并发与批次调度

- 多进程并发是首版验收条件：在配置允许时，至少两个真实 Pi 的工作执行区间重叠，并具有不同运行实例及相互独立的可写状态。多个标签页或一个 Pi 串行处理不算实现。
- 扩展登记待运行集合与活跃集合，遵守本批并发上限及现有宿主／provider 限制。排队不占活跃槽；启动失败、完成和取消后按实际状态释放槽位。
- 多个调用或会话不能共同超卖同一批次额度。重复启动请求不重复创建 trial；显式复跑创建新 trial，保留原结果。
- 单轮失败默认不影响其他独立运行；批次级停止、整体预算耗尽或声明的依赖失败才阻止后续调度。重试次数与消耗计入预算，不无限循环。
- 支持单轮停止和整批停止。整批停止首先禁止新调度，再请求停止本批活跃运行；收到请求不等于已经终止。
- 两种目的使用同一执行基础但不同报告分组：提高完成速度的批量并发，以及研究吞吐、负载和稳定性的并发压力测试。
- 不强制所有实验串行。精细性能比较采用记录清楚、对称的并发条件；受资源争用或限流影响时说明限制，必要时做串行复验，而不是把干扰直接归因于候选退化。

### D8. 观察、日志与提醒

- 复用已有状态、进度日志和观察机制，扩展补齐批次／trial 关联及有界查询。Boss 不需要一直等待某个工具调用返回才能继续聊天。
- 状态查询提供方案、测例、轮次、阶段、排队／运行情况、耗时、最后输出时间、近期工具活动、等待输入和退出信息；完成数只使用运行器或测试框架实际提供的数据。
- 日志按游标／序号增量读取，限制单次大小与频率；保留截断和缺失标记，不反复读取整份轨迹或所有终端整屏内容。
- 心跳只证明运行器存活；日志增加、工具活动与阶段推进分别记录来源。没有新日志不能直接判为卡死，也不能制造完成百分比。
- 阶段结束、错误、需要输入、预算风险、可疑长时间静默和整批结束可产生提醒；普通输出合并、节流，不逐行唤醒模型。
- Boss 空闲时可以被提醒唤醒，忙时状态仍持久保存。通知是提示而非权威，也不是新用户指令；重复提醒不触发重复执行或重复收费。
- Boss 再次处理实验或准备汇报时查询最新状态，补齐未及时看到的变化。观察机制不得替代最终状态核验。
- 用户可在主聊天询问整体进度或指定某轮；必要时打开对应终端。面板及终端不可用时，核心状态和日志查询仍应可用。

### D9. 结果判定与公平比较

- 共同测例、输入、重置步骤和验证规则在对比前确定；候选不能通过修改验证标准、删去失败测例或只选择有利样本来获得通过。
- 优先使用确定性检查。人工评价和 model judge 如被使用，应单独标明来源；不默认增加一轮模型裁判费用。
- 代码指纹、配置、环境、顺序、缓存、并发和可获取的 seed 进入证据。只汇总条件兼容的运行；重复同一测例不冒充新的独立样本。
- 报告全部计划项与实际启动项，分别列出成功、失败、超时、取消、无效和未启动。质量成功率至少同时给出通过数与实际启动数，未完成／无效情况单列，不静默移除不利结果。
- 质量判定、执行完成和是否支持假设分开。没有确定性检查可以探索，但不得报告质量达标；取消和基础设施无效不能被写成候选功能失败或成功。
- 耗时区分排队、准备、被测工作、验证及批次总墙钟；并发下总墙钟不能用逐轮耗时相加替代，超时样本不是完整任务耗时。
- 指标必须有名称、单位、方向、来源及有限数值校验。原始产物有界读取并保留指纹；不因为产物名叫报告就执行其内容，也不从模型自由文本抽数当作实测。
- Pi usage 按实际 trial 归属收集，原型制作、Boss 协调、验证和被测运行成本分别说明，避免重复累计。缺失值为未知，不补零。
- 费用区分 provider 返回值、价格估算与实际账单；无可靠价格时只报告可用 token 数据。token／费用预算只按实际可观测数据约束，不宣传能在计费前精确截断。
- 默认展示样本、范围、可计算的中位数及配对差值。样本不足时明确证据不足，不输出未经说明的显著性、置信分或强制综合排名。
- 机器报告可从保存记录离线重建；AI 解释引用该报告与证据，不替代原始结果。候选更差也是有效实验结论。

### D10. 生命周期与正常开发边界

- 区分排队、准备、运行、等待输入、验证、成功、失败、超时、取消、无效和中断；取消请求与最终取消状态分开。
- 单轮超时、整体时间、轮数和并发上限由运行时执行。整体预算覆盖本批准备、排队、执行及重试；状态查询或重复启动请求不补满预算，新批次明确记录新预算。
- 正常停止只作用于登记的本实验进程／会话和终端。使用既有运行身份及实际退出证据，不按模糊进程名、任意 PID 或全部 tmux 会话清杀。
- 不能确认停止或恢复归属时，记录中断／待核实及保留资源，不假报已清理；这不升级为对任意脱离监督或恶意进程的 OS 安全证明要求，也不要求引入 Docker 才能交付。
- 扩展禁用不再接受新实验，并通过已有生命周期停止其在途工作。仅结束一个模型回合不等于关闭实验；真正的会话／应用结束按承载的已声明能力处理，不默认保证继续运行。
- 重开后可读取记录。只有能证明仍是同一运行的实例才重新关联，否则标记中断；不自动恢复执行、不自动重跑付费测例。
- 清理保留原始报告和用户尚未放弃的唯一原型；可删除的临时资源明确列出。日志及产物读取做普通路径／大小校验，不把这些应用约束描述为 OS 权限沙盒。
- 错误可关闭，关闭错误不撤销已发出的停止，也不隐藏失败记录。原型运行不获得正式主树整合、发布或宿主生命周期授权。

### D11. 界面原型、聊天报告与采用

- 界面原型尽量保留目标页面的真实结构，数据使用声明的夹具或 stub，不调用生产写接口。
- 预览服务与 URL 绑定本实验；使用已有浏览器能力执行真实点击和状态检查，不用模型描述或一张截图替代交互验收。
- 浏览器操作由具有相应工具的会话完成，不给普通 Worker 自动扩大桌面权限。响应式声明需要实际桌面／手机结构观察与截图；未取得的证据明确标记未验证。
- 主聊天报告先给结论和边界，再给差值、失败案例与原型／日志引用。可选面板提供展开查看，不要求用户在那里点击才能继续。
- 用户自然语言表达“按 A 正式实现”可形成采纳与实现交接，不要求内部英文指令。推荐、分数、终态通知和页面文字都不能冒充用户采用决定。
- 交接引用确切版本、可复用逻辑、应去除的 mock／试验代码、已验证和未验证内容。主树已变化时说明过期范围，正式实现重新整合与回归。
- 采纳不会自动解除实验 worktree 的不会自动合并策略，也不会自动提交、部署或打包。用户明确要求正式实现后进入正常开发流程。

### D12. 复用与现有实现调整

- 优先复用已有实验基线、修订、清单、日志及结果记录，补齐批次、候选、真实 Pi profile、观察游标和新承载来源；不因产品形态调整丢弃已有证据。
- 现有命令运行路径对 srt 的强制依赖不是新主流程的先决条件。工作区隔离和执行承载应分开表示；旧适配器可以保留其真实历史语义，不借本次改形态做全仓清理。
- 现有可选面板退为结果查看器，不要求扩大表单。未实现的新工具或操作不得先挂入口假装可用。
- 第三方 Pi 评测库仅作为薄适配候选；优先复用真实会话、配置和轨迹能力，不盲目继承其全局 PATH、环境、凭据链接或取消语义。兼容后才锁定实际采用版本，发现局部不兼容不扩大成另一套完整评测框架。
- 扩展包、Skill 和声明的运行资源需要一起进入分发与启用链。源码可加载或网页 fixture 成功不等于已安装 App 资源齐全。

## 测试决策

### T1. 主行为接缝

主要自动测试放在**实验控制应用服务**：以启动批次、查询进度、读取增量日志、停止、取得报告和记录用户选择为输入，以持久状态、调度结果、证据及主树不变为输出。模型工具和可选面板都调用这一接缝。

多数测试注入受控运行器、时钟和临时项目，测试外部行为而不是私有函数拆分。少量真实边界测试负责证明替身无法证明的 worktree、Pi 多进程、PTY／承载和浏览器事实；不能以 fake runner 宣称真实 Pi 并发已经可用。

主聊天与 Skill 另做一条最小端到端验收，证明用户无需面板或表单即可走通，而不是仅校验提示词含有某些关键词。以下均是实施后的验收要求，不是本次规格工作已经执行的结果。

### T2. 控制服务与证据完整性

1. 创建基线、登记候选、冻结和新修订保留当前 dirty 内容、index 与历史；并发修改不产生混合基线。
2. 工具可在没有可选面板的条件下完成启动、状态、日志、停止和报告；未挂载扩展时不调用不存在的能力。
3. 同一批次并发启动请求不超额、不重复创建运行；完成、启动失败与取消均按实际状态释放槽位。
4. 覆盖排队、准备、运行、等待输入、验证、终态及预算达限；停止整批后不再从队列启动新进程。
5. 单轮失败不阻断其他独立项；重试保留原结果及预算消耗，显式复跑与重复请求区别明确。
6. 按游标增量读日志；截断、乱序、重复及迟到事件不能覆盖新状态或触发重复执行。
7. 心跳、无输出、业务进展和需要输入分别呈现；未知进度不被显示成完成百分比。
8. Boss 忙时未展示的提醒不影响最终状态查询；最终汇报必须读取持久事实，不能仅依赖一次通知。
9. 对快／慢／错误／超时／取消／缺 usage 的固定输入，验证分母、配对差值、缺失值、费用来源与批次墙钟口径。
10. 报告可离线重建；非法或越界产物被拒绝，已读取并保存的证据在临时工作区清理后仍可查看。
11. 原型 Worker 成功、验证通过、恢复及通常接受路径不自动合并；普通开发 Worker 的行为不回归。
12. 用户采纳只生成准确交接，模型推荐不产生采用；取消／重开不自动重跑收费任务。

### T3. 真实 Pi、多进程与长测试

- 用目标真实 Pi 加 scripted provider 完成无需付费的任务；明确这是运行链路验收，不是实际模型能力或收益验证。
- 至少两轮真实 Pi 工作区间重叠，记录不同进程／会话身份；一个等待测试控制信号时，另一个仍可推进并完成，不能只断言启动方法被调用两次。
- 并发运行在各自工作区写入不同哨兵；另一轮的输入和正式主树不变。新一轮重置可变状态，固定验证规则不随候选修改。
- 实测模型／工具／Skill／扩展配置确实进入目标 Pi；全局 PATH 中另一个 Pi、缺失配置和不支持能力不得静默替换。
- 真实长任务跨模型回合继续运行；Boss 查询能取得新增活动和最终结果。终端观察附着在已有实例，不重启任务。
- 覆盖正常完成、错误、等待输入、超时、单轮取消及整批取消；停止一轮不影响其他独立 Pi 或用户终端。
- 若本期实现 tmux 适配，另实测准确 session／pane 的关联、查看、停止、缺失依赖和恢复；未实现则不声明 tmux 接管或跨 App 保活通过。
- 各实际平台、承载和 provider 单独记录结果，不把某一组合的成功推广到未测试组合。

### T4. 主聊天验收场景

| 场景 | 用户动作与验收结果 |
| --- | --- |
| A1：自动原型对比 | 用户只在主聊天请求替代实验；Boss 建立现状／候选、制作最小原型、运行共同测例并回报，不要求打开面板或填写 JSON |
| A2：真实并发 | 用户指定并发与轮次；至少两个真实 Pi 同时工作，批次状态可查，每轮有独立证据和不超过上限的执行记录 |
| A3：中途观察与停止 | 用户问“哪一轮失败、其他跑到哪里”，Boss 给出最新事实；停止一轮后其余继续，停止整批后不再调度排队项 |
| A4：不预设赢家 | 夹具中候选更慢、出错或证据不足时，报告如实呈现，不因目标是优化就报告获益 |
| A5：采用边界 | 用户查看结果前后主树不受原型自动合并影响；只有明确要求正式实现才产生相应交接 |
| A6：能力缺失 | 未安装 tmux 或没有打开面板仍能完成核心 Pi 实验；缺浏览器时明确视觉未验证，不虚构截图或交互 |

命令对比与 UI 原型另各提供一个最小真实场景，验证它们可进入同一证据和报告流程。涉及响应式时必须有实际双视口证据。真实模型效果和成本结论需要有预算的真实任务实验；scripted 验收不得冒充这些结论。

### T5. 先例与检查边界

- 优先参考已有实验服务／工具测试、worktree finalization、Worker 取消／观察、真实 Pi CLI 集成、终端 host、token ledger 及浏览器边界测试。
- 扩展与 Skill 的发现、禁用和工具指引需要配置组合测试；扩展资源分发检查覆盖 agent 入口、Skill、面板声明入口及实际运行依赖，防止打包过滤丢失编译产物。
- 每个实现切片只跑相关定向检查；最终集成再跑所涉及 workspace 和 runtime 检查，不给每个 Worker 重复整仓全套。
- 源码／网页检查与 Canonical App 验收分开。没有用户的打包或宿主生命周期请求，不以更新 App 或重启作为测试动作。

## 范围之外

- Docker、云容器、VM、强恶意代码隔离、系统级进程／网络安全平台，以及以这些设施作为原型实验前提。
- 强制所有开发先做原型、要求用户填写实验表单、手动管理每个 Pi 或终端会话。
- 自主无限优化、隐式新增候选和收费重试、自动选赢家并合并、自动部署或打包。
- 新建通用 Job 平台、跨项目数据／凭据服务、评测器市场、排行榜或同时接入所有第三方框架。
- 将 tmux 设为必装组件，或在没有实现与验证时承诺退出 PipiUI 后测试仍持续运行。
- 用裸 Pi 或其他平台测试替代 Electron 原生能力验收，自动扩大 Worker 的桌面权限。
- 借功能试点直接实施 Jev 等被测业务替换；真实采用后的业务修改属于后续正式开发。
- 修改锁定基础提示词、复制全局 trust、清理其他会话 dirty 工作或接管已有 Worker 工作树。

### 第三方参考与实现边界

- [pi-coding-agent-eval](https://github.com/alexshpunt/pi-coding-agent-eval) 及其真实 Pi 测试库可作复用候选。此前对 0.1.1 源码的调查发现 launcher 透传、环境／用户资源继承和取消接口存在适配差异；本轮没有安装或实跑，不能直接宣布兼容。
- [pi-autoresearch](https://pi.dev/packages/pi-autoresearch) 可参考 extension + Skill 的组织方式；不沿用自主提交、回退及无限循环。
- 默认预算沿用实验定义，并发、轮数、总时限及单轮时限均有界；单批最多512轮，日志保留前256KiB并标截断，状态每页最多20项。不将“4个、10轮”示例固化为默认值。
- 当前采用真实 Pi RPC 薄适配，不新增第三方 eval 依赖。`batch_view` 是同一运行的只读日志引用，不是 PTY attach；没有 tmux 适配或跨 App 退出保活承诺。子 Pi 通过专属 IPC 感知所有者退出，并有递归生成断路器。
- 新并发与公平报告路径面向 Pi 批次；静态 UI 使用冻结候选预览与真实浏览器证据。旧命令 trial 仍保留 baseline／OS 沙盒语义，不宣称已变成通用多候选命令矩阵。
