## Philosophy: what the harness is trying to be

The central idea is not "a clever prompt around DeepSeek". It is a **composable agent operating system in which every capability is replaceable**. Cordis supplies a shared service context, typed events, declared dependencies, and reversible effects; tools, model adapters, the session log, and even the agent loop are plugins rather than a privileged core ([architecture lines 7-17](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/architecture.md#L7-L17), [Cordis primer lines 7-14](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/cordis-primer.md#L7-L14)).

Its second idea is **configuration as composition**. A runtime is an ordered plugin tree: bundles provide defaults, then profile, home, and command-line patches replace or insert rows. `web` and `headless` are compositions over the same base rather than separate products ([architecture lines 19-40](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/architecture.md#L19-L40)).

Its third idea is **durable, reconstructable agent behavior**. The append-only session event log is the source of model history; raw streaming chunks are retained; fork, resume, transcript, persistence, and telemetry derive from that log. The explicit invariant is "model-visible means logged" ([architecture lines 82-87](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/architecture.md#L82-L87)). A turn is a logged state machine of model steps and tool calls, while policy/interception happens through live waterfall events ([architecture lines 52-79](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/architecture.md#L52-L79)).

Its fourth idea is **capability seams instead of implementation coupling**: service definition, provider, and consumer are separate roles. Swapping the filesystem/subprocess world can move Bash, PTY, and LSP together; subagents can be in-process, fresh-process, Codex/Claude/ACP, or another compatible provider behind one interface ([architecture lines 89-104](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/architecture.md#L89-L104)).

## DeepSeek-model-specific optimizations

### 1. A native adapter instead of generic OpenAI compatibility

The `deepseek-official` route is a direct `fetch` + SSE adapter for DeepSeek chat completions, separate from its generic `pi-ai` adapter. It defaults to V4 Flash/Pro metadata, a 1,000,000-token context capacity, a 256,000-token output cap, and text-only input; exact deployment/model overrides remain possible ([adapter README lines 1-44](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/README.md#L1-L44)). This is the main optimization boundary: encode DeepSeek's actual protocol rather than hope a generic SDK interprets it correctly.

### 2. Correct thinking-mode control and selective reasoning replay

The adapter exposes only `off`, `high`, and `max`. `high`/`max` become `thinking.enabled + reasoning_effort`; `off` becomes `thinking.disabled` and omits the invalid wire value `reasoning_effort: off`; unsupported efforts fail before network I/O ([serializer lines 25-53](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/serialize.ts#L25-L53), [request serialization lines 151-186](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/serialize.ts#L151-L186)). Session-title requests force thinking off so the base composition's 64-token title budget is not consumed by hidden reasoning ([base title configuration lines 46-53](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/bundle/base/cordis.patch.yml#L46-L53)).

Most importantly, assistant `reasoning_content` is replayed **only when that assistant turn contains tool calls**. DeepSeek requires full passback on thinking-mode tool-call turns (or it returns 400), while plain-turn reasoning is ignored; dropping the latter saves later input tokens ([serializer lines 70-101](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/serialize.ts#L70-L101), [official thinking-mode rule](https://api-docs.deepseek.com/guides/thinking_mode)). This is a concrete DeepSeek optimization and correctness fix, not generic chain-of-thought handling.

### 3. DeepSeek streaming/tool-call quirks are normalized

The translator ignores the initial empty `reasoning_content`, keeps text, reasoning, and every tool call as separate indexed blocks, and accumulates tool arguments by the wire `tool_calls[].index`; this handles interleaved/fragmented parallel tool calls without corrupting arguments ([translator lines 86-179](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/translate.ts#L86-L179)). Finish and usage are held until `[DONE]`, covering both finish-attached and trailing usage-only chunks; EOF without `[DONE]` is a protocol error rather than a partial success ([SSE parser lines 17-40](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/sse.ts#L17-L40)).

The harness then validates/parses tool arguments, runs safe calls concurrently where declared, and commits results in the original model order. That execution scheduler is generic; only the wire translation above is DeepSeek-specific.

### 4. Prefix-cache discipline and truthful accounting

DeepSeek's disk context cache is automatic and prefix-based; the provider docs require matching persisted prefix units and expose hit/miss token counts ([official cache guide](https://api-docs.deepseek.com/guides/kv_cache)). The adapter does not invent a cache-control header. Instead it preserves stable prefixes through the generic prompt/session design, selectively removes unnecessary reasoning replay, and maps DeepSeek's inclusive `prompt_tokens` into disjoint harness counts by subtracting cache hits. It accepts both `prompt_cache_hit_tokens` and OpenAI-compatible `prompt_tokens_details.cached_tokens`; DeepSeek exposes no cache-write count ([translator lines 45-61](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/translate.ts#L45-L61)).

Compaction is also cache-aware: its auxiliary call repeats the prior request prefix byte-for-byte and adds one final instruction, maximizing reuse of the warm DeepSeek prefix; the conversation checkpoint itself replaces old history, so reuse is lost only from the first replaced token onward ([compaction lines 97-156](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/compaction/compaction-basic/README.md#L97-L156)).

### 5. DeepSeek-aware error classification and recovery

The adapter distinguishes authentication, quota, rate limit, context overflow, invalid request, server, transport, timeout, abort, malformed SSE, truncated stream, unknown finish reasons, and successful-but-empty output. It preserves valid `Retry-After` and DeepSeek/request IDs ([classification lines 117-149](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/adapter.ts#L117-L149), [HTTP handling lines 321-344](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/adapter.ts#L321-L344)). Empty responses become retryable errors; context overflow can trigger one durable compaction/retry rather than blindly replaying the oversized request ([LLM contract lines 204-220](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/subsystems/llm-streaming.md#L204-L220), [compaction lines 20-22](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/compaction/compaction-basic/README.md#L20-L22)).

### 6. What is *not* optimized or not found

- **No special DeepSeek system-prompt template** was found. The DeepSeek adapter explicitly adds no prompt prose; it receives the generic assembled system prompt/history/tool schemas ([adapter README model experience lines 77-93](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/README.md#L77-L93)).
- **No automatic Flash-versus-Pro router** was found. The default is Flash; provider/model changes are explicit configuration or `agent/request` middleware.
- **No DeepSeek-specific parallel execution scheduler** was found. Parsing is provider-specific, execution concurrency is generic.
- **No prompt-cache write/retention API** exists in the direct adapter; DeepSeek cache creation is automatic, and the adapter only reports read hits.
- **No tool-choice mapping** exists in the core/direct adapter, despite the upstream API supporting it; the adapter README marks it deferred ([known limitations lines 109-114](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/README.md#L109-L114)).
- **No image/multimodal path** exists in the direct adapter; it fails explicitly rather than silently dropping images ([serializer lines 55-68](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/src/serialize.ts#L55-L68)).
- **No public quality benchmark or ablation** was found, so claims that `dsh` materially raises DeepSeek coding scores are currently unverified by the official repository.

Important caveats:

- The advertised 1M context and 256K output values are adapter defaults/deployment metadata, not runtime discovery; the adapter deliberately does not clamp output against context, so deployments must configure honest limits ([adapter README lines 38-44](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/README.md#L38-L44)).
- Direct serialization flattens user/tool-result content to text, skips unknown extension blocks, lacks `tool_choice`, and uses raw `fetch` rather than the shared Cordis HTTP seam ([known limitations](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/llm/llm-deepseek/README.md#L109-L114)).
- The local sandbox controls file effects, not network or process visibility; do not treat it as a full security boundary ([sandbox lines 9-23](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/subsystems/sandbox.md#L9-L23)).

## Short integration implications for PipiUI

These are mostly external implications; one narrow, live PipiUI routing check was added because it exposed an immediately actionable mismatch.

1. A DeepSeek route should be treated as a **protocol adapter**, not just an OpenAI-compatible base URL: preserve `reasoning_content` on tool turns, parse indexed streaming calls, normalize usage/cache fields, and classify DeepSeek errors.
2. Stable, canonical prompt-section and tool-schema ordering plus append-only dynamic-context snapshots are likely the highest-leverage cache ideas to borrow.
3. Compaction should be route-capacity-aware, prune oversized tool output first, preserve tool-call/result pairing, replay the warm prefix for summarization, and retry overflow only after durable surface progress.
4. Provider-neutral seams and an event-sourced model-visible log are useful design references, but wholesale adoption of Cordis would be a large architectural choice; the smallest useful borrowing is the adapter/error/compaction contracts.
5. Do not claim a quality uplift from adopting these ideas without a PipiUI A/B evaluation; the official project currently publishes protocol correctness and architecture, not comparative coding benchmarks.

### High-value local finding: PipiUI's DeepSeek philosophy layers do not match the live provider route

A read-only probe of the isolated Electron profile's `settings.json` selected only three non-secret fields and found the current defaults are `defaultProvider: opencode-go`, `defaultModel: deepseek-v4-flash`, and `defaultThinkingLevel: off`; no credential or other setting was read into the report. PipiUI's philosophy extension formats the model identity literally as ``${provider}/${id}``, so this session becomes `opencode-go/deepseek-v4-flash` ([`formatModel`](../../Electron/resources/runtime/pi-philosophy/philosophy.ts#L147-L156)). Its matcher performs only case-insensitive exact match or a single trailing-`*` prefix; it intentionally does not infer model families ([`modelMatches`](../../Electron/resources/runtime/pi-philosophy/compose.ts#L171-L186)).

However, both DeepSeek correction layers are restricted to `requires-models: deepseek/deepseek-v4-*`: [`50-toolcall.md`](../../Electron/resources/runtime/pi-philosophy/layers/50-toolcall.md#L1-L9) and [`52-thinking.md`](../../Electron/resources/runtime/pi-philosophy/layers/52-thinking.md#L1-L9). Therefore the current `opencode-go/deepseek-v4-flash` route does **not** receive either layer. The same structural miss applies to the same model served through `volcengine`, `jellytoken`, or any provider id other than literal `deepseek`.

This matters because the official harness's strongest DeepSeek work is precisely tool-call discipline, reasoning control/passback, and provider-protocol handling. Suggested follow-up, without changing code here: make model-scoped philosophy selection capable of expressing a verified model family/capability, or enumerate trusted provider/model routes. Matching only the bare model id would be convenient but would also let an unrelated provider reuse a DeepSeek-looking id, so an explicit trusted-provider or capability-provenance rule is safer. Separately, the live default thinking level being `off` means PipiUI is not exercising DeepSeek's thinking-mode path by default; that is a product/config choice, not evidence that the model lacks thinking support.
