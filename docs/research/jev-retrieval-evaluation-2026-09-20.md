# Jev 检索对比：覆盖与排序改善，单次延迟增加

日期：2026-09-20。以下为实际执行结果，不是估算或模拟 Jev 评分。没有上传当前工作区源码；真实 API 只接收新生成的合成代码。密钥仅经安全保险库和环境变量使用，没有写入仓库或报告。

## 结论

**目前不能声称「更快且保证正确性」。** 本地宽召回提高了这批真实仓库问题的覆盖；Jev 提高了合成干扰场景的排序准确率，但增加了单次检索延迟。是否能靠减少主 LLM 的往返来抵消成本，尚未测量。

因此保持 `jev-optimizer` 独立、默认关闭、显式启用；它目前是可选的相关性质量优化，不是已经证明的端到端加速。

## 1. 接口连通性

首次真实 smoke 只使用两段合成函数：刷新访问 token 与设置主题。

- 实际模型：`jev-1.13.0`。
- 耗时：631 ms。
- 输入用量：574 tokens。
- 得分：刷新函数 2.79/3；主题函数 0。

它只证明当前 key 和适配器可用，不能证明检索收益。

## 2. 真实仓库，本地 A/B

使用 30 个磁盘验证通过的金标问题，各重复 3 次；每组 90 次测量。A/B 使用同样的最终 topK、范围和输出预算，顺序按重复轮次交替。描述型案例使用明确的 semantic 模式；精确／符号控制组不加变体。共享索引没有被终止或清空，初次观测不等于冷索引。

| 指标 | A 单查询本地 | B 宽召回本地 |
| --- | ---: | ---: |
| Recall@12 | 70.0% | 83.3% |
| Recall@3 | 36.7% | 53.3% |
| 检索 P50 | 20 ms | 61 ms |
| 检索 P95 | 105 ms | 87 ms |
| 输出 token 估计中位数 | 528 | 568 |

- Recall@12 增加 13.3 个百分点，但 P50 增加 41 ms；输出估计也没有降低。
- P95 的差异受索引状态、顺序和小样本影响，不能单独据此宣称提速。异常清理修复后又完整复跑一次：召回率保持相同，A 的 P50/P95 为 19/83 ms，B 为 61/117 ms，再次不支持单次提速。
- B 仍有 5/30 个问题未进入前 12 项，包括 UI 队列、vault 环境及符号提示查询；不是全正确。
- C（该真实仓库候选 + Jev）和该仓库的单查询+Jev 没有运行：没有把工作区源码外发授权等同于提供 key。
- 验证 PASS 指金标、预算、来源和测量完整性，而不是性能目标达成。

命令：

```bash
cd Electron
node resources/runtime/extensions/code-retrieval/agent/eval/run-retrieval-eval.mjs \
  --jev-contrast --repetitions 3 --json /tmp/pipiui-jev-offline-contrast.json
```

原始有界报告：`/tmp/pipiui-jev-offline-contrast.json`，旁有 `.md`；只含指标，不导出源码／query。此次仅清理自己明确收到的 180 个结果文件；没有终止 sidecar。最终复跑结果位于 `/tmp/pipiui-jev-offline-final.json`，同样 180/180 清理、0 个未结束任务、验证 PASS。

## 3. 合成代码，真实 Jev 配对

10 个不同任务，各重复 3 次；40 个生成文件，包含会执行目标操作的实现，以及使用相近词语但仅记录日志、提供配置或显示标签的干扰项。这是人工构造的语义消歧压力场景，**不是独立真实仓库样本，也不是 LLM 基线**。

索引先构建；A/B 的候选预算均为 100。C 对 B 的同一批返回候选做生产重排，单查询+Jev 对 A 的同一批返回候选做重排。每一对都检查候选路径和行范围集合不变。时间是本地阶段与重排阶段的分段累计，不包含完整 Agent 规划、阅读、编辑和验证。

| 方案 | Top1 | Recall@3 | Recall@12 | P50/P95 分段累计 | 应用/回退 | 输入 tokens |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A 单查询本地 | 50.0% | 60.0% | 80.0% | 20/31 ms | — | 0 |
| B 宽召回本地 | 90.0% | 90.0% | 100.0% | 54/85 ms | — | 0 |
| C B 的同候选 + Jev | 100.0% | 100.0% | 100.0% | 492/744 ms | 30/0 | 226,041 |
| A 的同候选 + Jev | 100.0% | 100.0% | 100.0% | 458/690 ms | 30/0 | 224,439 |

- 共 60 次真实 API 请求，全部成功应用；输入用量合计 450,480 tokens。
- Top12 新增漏检为 0，候选集合没有被增删；不表示未来任何问题都不会错。
- B → C 的 Top1 从 90% 到 100%，但 P50 从 54 ms 到 492 ms，单次路径明显更慢。
- 实际费用没有从账单取得，不将公开价格估算伪装成支出结果。
- 只有 10 个独立任务；重复 3 次不等于 30 个独立任务，不据此给出泛化正确率保证。

## 4. 正确性保障与边界

自动契约覆盖默认关闭／缺 key／故障回退、范围与符号链接限制、保留强精确命中、R# 到原文的对应、严格响应校验（含重复 JSON key）、取消传播与 key/启用代际撤销。

最终回归为 146 项检索／Jev Node 测试、168 项宿主测试、68 项评测单元测试通过，相关 TypeScript 检查通过。评测器还验证了强制超时：退出码为 1、`execution-incomplete`，11/11 本轮产物清理；工具错误不能被排除分母后伪装成 PASS。

这些约束保障「不凭空添加路径、不因服务失败丢掉本地候选、不在取消后继续新查询」；**它们不等于模型的相关性判断永远正确**。语义判断仍可能排错，已知标识符应继续使用精确工具，关系问题继续使用符号图。

当前项目 secret 沿用宿主现有项目隔离内存 namespace；没有新增永久凭据存储。扩展设置中的新 key 按新会话／Pi 子进程刷新规则生效，宿主退出后需要重新配置该项目 secret。本次测试使用会话安全挂载，不代表运行中的旧 App 已安装或配置新扩展。

## 5. 尚未证明的事项

- 原规格的 20% 整体耗时／输入节省实验目标。
- 相比直接使用 LLM 排序的同输入公平对照。
- 当前打包 App 的实际界面验收：本轮只做源码与 workspace 验证，没有打包或重启。

不能将「排序更准」直接改写成「整个 Agent 更快」。下一轮若做端到端验证，应固定任务与模型、允许外发的数据集及预算，同时统计失败和回退，不能只挑成功案例。
